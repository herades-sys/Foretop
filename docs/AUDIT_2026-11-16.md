## 2. Replay renderer: root cause

The minimap places a ship at world (x, z) with `screen = map rect + (x − minX, maxZ − z) × scale`, where the map
size comes from the map's `space.settings`. `ReplayLibrary.PlayableHalf` read the chunk bounds only as child
elements:

```xml
<bounds><minX>-9</minX><maxX>8</maxX>…</bounds>          (5 maps)
```

but 53 of the 58 maps with a minimap write them as attributes, without `chunkSize`:

```xml
<bounds minX="-10" maxX="9" minY="-10" maxY="9" />       (53 maps)
```

For those the parser found nothing and silently used the defaults of 28_naval_mission (±700). Measured over every
map in the game files (`foretop-probe spaces`):

| Real playable half-size | Maps | Effect before the fix |
|---|---|---|
| ±800 | 20 | ships drawn 14 % too far from the centre, beyond the map edge near the borders |
| ±700 | 22 | correct (by luck of the default) |
| ±600 | 6 | ships pulled 14 % towards the centre |
| ±500 | 4 | 29 % towards the centre |
| ±400 / ±300 / ±100 | 3 / 2 / 1 | 43 % / 57 % / 86 % towards the centre |

The error grows with the distance from the map centre, so it looks like wrong scaling and drifting alignment.
Islands, capture points and smoke were affected the same way (all used the same scale). Only X bounds were read,
so a non-square map could not have been drawn correctly either.

Checked and found correct: X/Z orientation (north up, east right), world origin at the map centre, images
covering exactly the playable area (two chunks inside the chunk bounds), heading of the markers, DPI (all drawing
in device-independent units), the UI text scale (layout transform, applied evenly).

## 3. Replay renderer: changes

- `Core/Replays/MinimapProjection.cs` (new): `MapBounds.FromSpaceSettings` reads both forms, X and Z separately,
  default chunk size 100, a fallback marked `Known = false` (shown on the map as "Map size unknown"), and full chunk
  bounds for tiny spaces. `MinimapProjection` is the single world↔screen transform: fit without distortion,
  centred, zoom 1–8× around a point, pan, clamped so the map never leaves the view, camera stored in map fractions so
  resizing keeps the same view. `ReplayLibrary.PlayableHalf` is removed; `MapAssets` carries `MapBounds`.
- `Views/ReplayCanvas.cs`: every element (images, grid, grid labels, capture points, smoke, trails, markers, labels,
  health bars, overview, debug) goes through one projection per frame. Mouse wheel zooms at the pointer, drag pans,
  double-click shows the whole map; an overview inset shows the visible part while zoomed. Trails now end at the
  interpolated position (they used to stop at the last recorded point, slightly behind the marker). Labels use the
  chosen UI font. The gap rule shared with interpolation (`SceneShip.MaxGap`).
- Debug overlay (Debug switch): map bounds, world origin, map centre, 100-unit grid with coordinates, space name,
  view and map rectangle, scale, zoom, camera, DPI, canvas size, last frame time, cursor world position, coordinates
  of every ship.
- `Views/ReplaysView.xaml`: the timeline has its own full-width row (it was squeezed to about 60–130 px); controls
  wrap below it; zoom buttons; **Full view** (F / Esc) hides the replay list and teams; side panels get narrower on
  small windows. Keys: Space, + / −, 0, F, Esc.
- Developer switches: `--window WxH`, `--replay-debug`, `--replay-full`, `--replay-zoom z[,x,z]`,
  `--render-minimap WxH,… <folder>` (renders the minimap off screen at any size).
- `tools/Foretop.Probe`: `spaces` (bounds and image sizes of every map) and `mapfit <replay>` (share of ship
  positions on island pixels for the current and alternative transforms, and heading vs direction of travel).

## 6. Remaining known issues (not fixed)

- **Replays of other maps**: bounds of the 53 attribute-form maps are verified from the game files only; a replay of
  a ±800 and a ±500 map should be run through `foretop-probe mapfit` (expect well under 1 % of positions on islands).
- L1: the Dashboard status timer counts cached responses every 2 s, also while hidden (small query; left).
- L8: turning detection off waits up to 3 s for the watcher on the UI thread.
- L11: the History row cache keys on summary lengths; a re-saved summary of the same length is not re-read (rarer
  now that H1 stops refresh rewrites).
- L14: the backfill and the replay enricher can both rewrite a result's extras; the next run restores them.
- U2: SQLite shared cache with WAL; no lock errors seen in the logs.
- Windows display scaling 125–200 % not tested on a real setting (see 4).

## 7. Analytics: global filters and tier analysis (new)

Architecture: `Core/Personal/Analytics.cs` turns both data sources into one record type (`AnalyticsRecord`: a
recorded battle, or a ship's account totals), filters them with one `AnalyticsFilter` (tiers, minimum battles per
ship, period, last N, class, nation, ships, battle type; `Intersect` for chart filters) and sums them with one
`AggregateStats` (totals ÷ battles; PR from summed actuals against summed expected values). The page
(`PersonalAnalyticsViewModel` + `.Explorer.cs`, `AnalyticsFilterViewModel`, `AnalyticsPanels.cs`) only displays.
Filtering runs in memory on data loaded once per reload: no API call or database query per filter change.

Verified with real data (your account, 144 Random battles on 31 ships):

| Check | Result |
|---|---|
| Tier VIII+ in the new filter | 51 battles, 54.9 % win rate = the independent recount from the raw API JSON (2026-11-15) |
| Tier rows add up | Tier I–IX rows 139 battles + 5 battles of then-unknown-tier ships = 144; after the fix all 144 are placed |
| Preserved ships (Kirov < 2020, Salmon/Balao/Cachalot < 2022) | tier from the game files; they were "unknown" only while the game data loaded (fixed: records are re-resolved when it arrives) |
| Tier VIII vs X battleships | 0 and 0 battles, every value "—" (you have none), no zeros invented |
| Recorded source (40 synthetic battles) | period, tier, PR over time with the account PR as reference line |

Automated: `AnalyticsTests` (13) — weighted win rate (not mean of ship win rates), draws, PR identical to
`PersonalRating.Compute` and to the period PR of recorded battles, missing values null, combined filters, unknown tiers
never match a tier filter, date filters need dates, chart filters only narrow (disjoint → nothing), last N then minimum,
grouping by tier/class, rankings respect the minimum and skip missing values, PR progression on running totals.

Limits (by design, stated on the page): the account totals have no dates or battle types, so period and type apply to
recorded battles; base XP exists only for recorded battles with a replay; PR over time needs recorded battles.

## 16. Real replays (29 files, 22 maps)

29 replays (1–15 November, 22 maps, 9 with ±800 bounds and 13 with ±700; none of them uses ±500) were checked with
`foretop-probe mapfit` and, for five maps, by snapshots of the app.

- **Map size and orientation: correct on every map.** Share of ship positions on island pixels with the bounds from
  space.settings: 0.00–1.6 % for 27 replays, 2.0–2.7 % for the others. Mirrored or rotated maps give 3–32 %, and a
  map 50 units smaller or larger is worse in every replay. The best-fit search lands on the space.settings size (±10
  units) for all but two carrier replays. Heading against direction of travel: median 2–5° everywhere.
- The higher values all come from carrier battles. A per-ship breakdown (`mapfit <replay> --per-ship`) shows why: the
  recording player's avatar (the plane camera) also has a position track, flies over islands and points anywhere.
  Ships in those battles are at 0 % on islands. The renderer only draws tracks of players, so nothing wrong is drawn.
- **Found and fixed: replays from an older game version.** The four replays of 15.9 (build 13357625, 1–2 November)
  lost their player list and about 1,500 events each: method and property numbers change between versions, and they
  were read with the definitions of the installed 15.10. Foretop now reads the replay's build from its header and,
  when that build folder is still on disk (the game keeps the previous one after an update), loads its definitions
  (the old index is released again). All four now decode with no warning: names, teams, health, kills. When the
  build is gone, the replay opens with the current definitions and a note says that names or events may be missing.
  Repeated warnings are reported once. Tests: client build from the header, note first and no repeats, missing build.
- `--replay <path>` now also opens a file outside the game's replay folder (used for the checks).

Still open: a ±500 map (small low-tier maps) has not been seen in a real replay; its bounds are checked from the game
files only.
